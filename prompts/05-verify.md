# 05 - VERIFY：运行验证

> **阶段目标**：证明改造生效了，不是"没报错就是对了"。
>
> 根据项目模式选择对应分支。

---

## 分支A：改造现有项目 → VERIFY

### 执行AI提示词（发给窗口B）

```text
【阶段：VERIFY】执行验证流程，带进度标记。

【执行铁律】
- 每完成一步，输出 [STEP X/5: 步骤名]
- 如果失败，输出 [STEP X/5 FAILED: 原因] 并停止
- 用户可能中途停止并指定"从第X步继续"
- VERIFY阶段只运行不改代码

步骤清单：
1. 保存所有修改的代码文件
2. 重启 Flask/服务（后台启动，不阻塞）
3. 等待3秒，确认服务就绪
4. 发送测试请求到 {{PROBE中找到的API路径}}
5. 读取日志，筛选包含 [PROBE] 的行，输出分析

开始执行。
```

### 等待执行AI返回

你会收到带 `[STEP X/5]` 标记的执行结果。

### 如果执行AI卡在某一步

- 停止执行AI
- 发送：`从第X步继续`

### 最终返回

执行AI会返回日志内容。

把完整返回（特别是日志部分）复制下来。

### 策略AI提示词（发给窗口A）

把 `{{Mimo的VERIFY返回}}` 替换为你复制的内容：

```text
【VERIFY分析任务】

请分析以下Mimo返回的验证日志。

## Mimo的VERIFY返回：
{{Mimo的VERIFY返回}}

## 你的任务：

### 第一步：日志分析
1. 【PROBE日志存在？】是/否。证据：
2. 【分析节点/新逻辑被调用？】是/否。证据：
3. 【模型返回了什么？】原始响应：
4. 【是否触发降级？】是/否。证据：
5. 【关键词/输出是模型结果还是旧逻辑？】判断：

### 第二步：根因判断
根据日志，根因是什么？

### 第三步：下一步决策
- 如果改造已生效（日志证明新逻辑运行正常）：输出【DONE】指令（见 06-done.md）
- 如果分析节点返回空/降级触发：输出【CODE-修复】指令（回退到 04-code.md）
- 如果分析节点没被调用：输出【CODE-调用链修复】指令（回退到 04-code.md）
- 如果模型调用失败：提示用户检查模型服务（Ollama等）
- 如果日志完全不存在：输出【CODE-日志修复】指令（回退到 04-code.md）
```

### 下一步

- 策略AI说"改造已生效" → 复制【DONE】指令，进入 [06-done.md](06-done.md)
- 策略AI说"需要修复" → 复制对应的【CODE-修复】指令，回到 [04-code.md](04-code.md)

## 分支B：从零新建项目 → VERIFY

> **目标**：证明功能满足验收条件，不是"没报错就是对了"。
> 验收条件由用户在 INIT 阶段定义，VERIFY 时对照检查。

### 执行AI提示词（发给窗口B）

```text
【阶段：VERIFY-从零】执行功能验收，带进度标记。

【执行铁律】
- 每完成一步，输出 [STEP X/N: 步骤名]
- 如果失败，输出 [STEP X/N FAILED: 原因] 并停止
- 用户可能中途停止并指定"从第X步继续"
- VERIFY阶段只运行不改代码

验收条件清单（INIT阶段定义）：
{{列出INIT阶段定义的验收条件}}

请执行以下验收步骤：

1. 【环境检查】确认所有依赖已安装，配置文件正确
2. 【启动检查】启动项目，确认无报错，服务就绪
3. 【功能验收1】{{验收条件1}} — 执行操作，记录结果
4. 【功能验收2】{{验收条件2}} — 执行操作，记录结果
5. 【功能验收N】{{验收条件N}} — 执行操作，记录结果
6. 【异常验收】故意触发异常场景，验证异常处理是否按CONTRACT设计工作
7. 【汇总】输出验收结果汇总表

每步输出格式：
[STEP X/N: 步骤名] ✓ 通过 / ✗ 失败（原因）

开始执行。
```

### 等待执行AI返回

你会收到带 `[STEP X/N]` 标记的验收结果。

### 如果验收失败

- 停止执行AI
- 把失败的步骤和原因发给策略AI分析
- 策略AI会判断是需要修复代码还是调整验收标准

### 策略AI提示词（发给窗口A）

把 `{{Mimo的VERIFY返回}}` 替换为你复制的内容：

```text
【VERIFY-从零分析任务】

请分析以下Mimo返回的验收结果。

## Mimo的VERIFY返回：
{{Mimo的VERIFY返回}}

## 你的任务：

### 第一步：验收结果分析
1. 【环境检查通过？】是/否。证据：
2. 【启动检查通过？】是/否。证据：
3. 【功能验收通过率】通过X/N项
4. 【异常验收通过？】是/否。证据：
5. 【哪些功能验收失败？】列出失败项和原因

### 第二步：根因判断
对每个失败项，分析根因：
- 是代码逻辑错误？
- 是接口不一致？
- 是配置问题？
- 是验收标准不合理？

### 第三步：下一步决策
- 如果所有验收通过：输出【DONE】指令（见 06-done.md）
- 如果有功能验收失败：输出【CODE-修复】指令（回退到 04-code.md）
- 如果验收标准不合理：输出调整建议，让用户确认后重新验收
- 如果环境/配置问题：输出排查指令
```

### 下一步

- 策略AI说"全部通过" → 复制【DONE】指令，进入 [06-done.md](06-done.md)
- 策略AI说"需要修复" → 复制对应的【CODE-修复】指令，回到 [04-code.md](04-code.md)
