# 01 - PROBE / INIT：摸清现状 / 从零初始化

> **PROBE 阶段目标**：让执行AI去代码库里查清楚"现在是怎么实现的"，防止在错误假设上堆代码。
> **INIT 阶段目标**：从零设计项目骨架，确认技术栈、目录结构、依赖规划。

---

## 模式选择

请根据你的项目状态选择对应分支：

- **模式A：改造现有项目**（代码库已存在）→ 使用【分支A：PROBE】
- **模式B：从零新建项目**（无代码库）→ 使用【分支B：INIT】

---

## 分支A：改造现有项目 → PROBE

### 执行AI提示词（发给窗口B）

```text
【阶段：PROBE】只查询，不改代码，不生成代码，不执行系统命令。

需求：{{你的需求}}

请对当前代码库进行全面探测，回答以下问题。每个问题必须具体到文件名、方法/函数名、类名、行号范围。如果项目有前后端分离，请分别列出前端和后端。

1. 【现状定位】当前实现该需求的代码在哪？
   - 后端：列出所有相关文件、方法/类、关键代码片段
   - 前端：列出所有相关组件/页面、方法、关键代码片段

2. 【调用链】触发该功能的完整调用链是什么？
   - 从用户操作/请求入口到最终处理，用 → 表示每一步
   - 例如：用户输入 → API路由 → 控制器 → 服务层 → 模型方法

3. 【外部能力】项目已有的模型调用/AI分析/外部API封装在哪？
   - 什么文件？什么方法？调用方式是什么？
   - 如果有统一的模型调用基类/工具，请列出

4. 【数据结构】核心数据结构定义在哪？
   - 实体类/数据模型/接口定义的文件位置
   - 关键字段名和类型

5. 【判断逻辑】相关的条件判断、循环处理是批量还是逐条？在哪实现？

6. 【扩展点】如果要新增模块/组件，按项目结构应放在哪个目录？命名规范是什么？

要求：
- 贴出关键方法的完整代码（不要省略）
- 文件路径用代码块标记
- 最后输出 [PROBE_DONE]

【v1.1补丁：代码库过大时】
如果代码库文件数量超过50个，或你无法在一次回复中完成全部探测：
1. 先列出所有相关文件（不超过10个）
2. 优先探测与需求最直接相关的3-5个文件
3. 输出时注明"已探测X个文件，剩余Y个文件待探测"
4. 等待用户确认后，再继续探测剩余文件
```

### 等待执行AI返回

你会收到一份探测报告（6个问题的答案 + `[PROBE_DONE]`）。

把完整返回复制下来。

### 策略AI提示词（发给窗口A）

把 `{{执行AI的PROBE返回}}` 替换为你复制的内容：

```text
【PROBE审查任务】

请审查以下执行AI返回的PROBE结果，并判断代码状态。

## 执行AI的PROBE返回：
{{执行AI的PROBE返回}}

## 你的任务：

### 第一步：完整性审查
检查以下项目，打勾或打叉：
- [ ] 6个问题全部回答（数一下，1-6都有）
- [ ] 有具体的文件路径（能看到 xxx.py 格式）
- [ ] 有方法/函数名和行号范围
- [ ] 关键代码完整贴出（不是只有方法签名）
- [ ] 末尾有 [PROBE_DONE] 标记
- [ ] 如果涉及前端，PROBE有前端部分

如果以上有任何一项未通过，输出【追问指令】，要求执行AI补充缺失项。

### 第二步：状态判断（最关键）
根据PROBE结果，判断代码处于以下哪种状态：

**状态A：全新**
- 完全没有相关新代码
- 只有旧逻辑（如正则分词、字符串匹配）
- 没有 analysis_node.py 或类似的新模块

**状态B：部分**
- 有新代码文件但未生效，或新旧混杂
- 调用链已改但运行时走旧逻辑
- 之前改崩过，有残留代码
- 用户明确说"之前改过了但没生效"

**状态C：已完成**
- 代码存在且PROBE显示逻辑正确
- 调用链完整，无残留旧逻辑

请明确输出状态判断：A / B / C
并给出判断依据（引用PROBE中的具体证据）。

### 第三步：输出下一阶段指令

根据状态判断，输出对应的下一阶段指令：

- 如果状态A（全新）：输出【DESIGN-新建功能】指令（见 02-design.md 分支A）
- 如果状态B（部分）：输出【DESIGN-诊断】指令（见 02-design.md 分支B）
- 如果状态C（已完成）：输出【VERIFY-验证】指令（见 05-verify.md）

指令必须是可直接复制给执行AI的完整提示词。
```

### 策略AI审查通过后

你会收到：
- 完整性审查结果
- 状态判断（A/B/C）
- 下一阶段指令（可直接复制给执行AI）

**检查状态判断是否合理**。如果策略AI说"状态B"但你觉得应该是"状态A"，告诉它修正。

复制策略AI生成的下一阶段指令，进入 [02-design.md](02-design.md)。

## 分支B：从零新建项目 → INIT

### 执行AI提示词（发给窗口B）

```text
【阶段：INIT】从零新建项目，先搭建骨架，不改代码。

需求：{{你的项目需求}}

请回答以下问题。每个问题必须给出具体建议和理由。如果存在多种技术选型，列出选项和利弊对比。

1. 【技术选型】根据需求，推荐技术栈
   - 前端：框架、UI库、构建工具（如适用）
   - 后端：语言、框架、ORM（如适用）
   - 数据库：类型、版本（如适用）
   - 部署：目标平台、容器化方案（如适用）
   - 每个选择说明理由

2. 【目录结构】设计项目目录树
   - 用树状图展示完整目录结构
   - 每个目录/文件说明放什么内容
   - 标注哪些是核心模块、哪些是辅助模块

3. 【依赖规划】核心依赖有哪些？
   - 列出所有需要安装的依赖包
   - 建议版本号
   - 标注哪些是必须的、哪些是可选的

4. 【入口设计】主入口文件是什么？
   - 启动方式（命令行/脚本/双击）
   - 启动参数（如有）
   - 开发环境和生产环境的区别

5. 【配置设计】需要哪些配置文件？
   - 环境变量列表（名称、用途、默认值）
   - 配置文件格式（YAML/JSON/TOML/.env）
   - 哪些配置必须用户填写、哪些有默认值

6. 【扩展预留】未来可能扩展的模块
   - 预留什么接口/目录
   - 当前不实现但需要在架构上预留的位置

7. 【验收标准】你希望怎么证明这个项目"做完了"？
   - 功能清单：哪些功能必须可用？（例如：能添加待办、能标记完成、能删除）
   - 验收测试：怎么验证这些功能？（例如：发送测试请求，预期返回什么）
   - 性能/稳定性要求：有没有并发、响应时间等要求？

要求：
- 只输出设计，不生成代码
- 如果有不确定的技术选型，列出选项和利弊，等待用户确认
- 输出 [INIT_DONE]
```

### 等待执行AI返回

你会收到项目设计方案（7个答案 + `[INIT_DONE]`）。

把完整返回复制下来。

### 策略AI提示词（发给窗口A）

把 `{{执行AI的INIT返回}}` 替换为你复制的内容：

```text
【INIT审查任务】

请审查以下执行AI返回的项目初始化方案。

## 执行AI的INIT返回：
{{执行AI的INIT返回}}

## 你的任务：

### 第一步：完整性审查
检查以下项目：
- [ ] 7个问题全部回答
- [ ] 技术选型有具体框架名和版本号
- [ ] 目录结构有完整的树状图
- [ ] 依赖列表有包名和版本
- [ ] 入口文件和启动方式明确
- [ ] 配置文件清单完整
- [ ] 验收标准具体可测试（有功能清单和验收方式）
- [ ] 末尾有 [INIT_DONE] 标记

如果以上有任何一项未通过，输出【追问指令】。

### 第二步：技术选型确认
检查技术选型是否合理：
- 是否与用户需求匹配？
- 是否有明显的兼容性问题？
- 依赖数量是否合理（不要过度依赖）？

如果有问题，指出并建议修正方案。

### 第三步：输出下一阶段指令

如果审查通过，输出【DESIGN-架构设计】指令（见 02-design.md 分支C）。

指令必须是可直接复制给执行AI的完整提示词。
```

你会收到：
