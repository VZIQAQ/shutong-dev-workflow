# 09 - DEPLOY：部署上线

> **阶段目标**：将验证通过的项目部署到生产环境，确保线上正常运行。
>
> 适用于从零新建项目。改造现有项目的部署由用户自行处理。

---

## 执行AI提示词（发给窗口B）

```text
【阶段：DEPLOY】部署上线，带进度标记。

【执行铁律】
- 每完成一步，输出 [STEP X/6: 步骤名]
- 如果失败，输出 [STEP X/6 FAILED: 原因] 并停止
- 用户可能中途停止并指定"从第X步继续"
- DEPLOY阶段只执行部署操作，不修改业务代码

部署目标：
- 项目：{{项目名称}}
- 目标平台：{{服务器/云平台/本地}}
- 部署方式：{{手动/自动}}

步骤清单：

1. 【环境检查】
   - 确认目标环境就绪（服务器/容器/云平台）
   - 确认环境变量已配置（列出所有必须的环境变量）
   - 确认依赖版本与开发环境一致

2. 【依赖安装】
   - 在目标环境安装项目依赖
   - 验证依赖安装成功（无报错，版本正确）

3. 【构建打包】（如有构建步骤）
   - 执行构建命令
   - 验证构建产物完整

4. 【部署执行】
   - 按部署方式执行上线
   - 记录部署日志

5. 【冒烟测试】
   - 访问线上地址/接口
   - 验证核心功能正常（至少3个核心接口/页面）
   - 记录响应时间

6. 【监控确认】
   - 确认日志输出正常（无ERROR）
   - 确认监控指标正常（如有）
   - 确认告警规则已配置（如有）

每步输出格式：
[STEP X/6: 步骤名] ✓ 通过 / ✗ 失败（原因）

【回退策略】
- 部署失败时：{{回滚方式，如"恢复上一版本的备份"}}
- 数据迁移失败时：{{数据恢复方式}}
- 线上出现严重BUG时：{{紧急回滚流程}}

输出末尾加 [DEPLOY_DONE]
开始执行。
```

---

## 等待执行AI返回

你会收到带 `[STEP X/6]` 标记的部署结果。

### 如果部署失败

- 停止执行AI
- 把失败的步骤和原因发给策略AI分析
- 策略AI会判断是需要修复代码还是调整部署方案

---

```text
## 你的任务：

### 第一步：部署结果分析
1. 【环境检查通过？】是/否。证据：
2. 【依赖安装成功？】是/否。证据：
3. 【构建打包成功？】是/否/跳过。证据：
4. 【部署执行成功？】是/否。证据：
5. 【冒烟测试通过？】是/否。证据：
6. 【监控确认正常？】是/否。证据：

### 第二步：下一步决策
- 如果所有步骤通过：输出【ALL_DONE】指令（见 06-done.md）

- 如果冒烟测试失败：输出【CODE-修复】指令（回退到 04-code.md）
- 如果监控异常：输出排查指令
```

## 部署检查清单

确认以下事项：

- [ ] 目标环境就绪
- [ ] 环境变量已配置
- [ ] 依赖安装成功
- [ ] 构建打包成功（如有）
- [ ] 部署执行成功
- [ ] 冒烟测试通过（核心功能正常）
- [ ] 日志无ERROR
- [ ] 监控正常
- [ ] 回滚方案已确认
